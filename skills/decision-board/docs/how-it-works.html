How the Decision Board Works

An agent works on a task and needs your answer: a choice, an approval, or an action that only you can do. It puts the question on a board. You answer on any signed-in device, whenever you have a minute. The agent reads your answers later and continues.

The board is one private claude.ai artifact: a web page with a small database. Many agents can share one board. Each answer goes back to the agent that asked.

Use it when you are away from the terminal, when questions pile up, or when an answer must outlive the agent's session. For one quick question, the terminal is faster.

Who does what

Six parts work together. Two are people or agents, four are files and data.

You, the operator

Open the board on any signed-in device. Tap an option, add a note, press Send.

The agent

A Claude session that follows SKILL.md. It posts cards and guides, reads your answers, and acts on them.

The page

assets/board.html, published once as the artifact. It never changes per board. It shows what is in the database.

The database

Belongs to the artifact. Holds collections of small JSON documents: cards, your answers, batches, guides, the config.

The script

scripts/board.mjs. Runs on the agent's machine with Node. Turns files into exact database writes, so the agent does not type them.

The watcher (optional)

A cheap background agent that polls the board and says "a new batch is there". It does not act on answers.

One round trip

This is the whole cycle for one question. Blue steps happen on the agent side, green steps are yours.

1. PostThe agent writes a card file and runs cards. The script prints the writes, the agent sends them.items/…
2. AnswerYou see the card, tap an option, maybe type a note. The page saves it as a draft.responses/…
3. SendYou press Send. The page bundles your answers into one batch per agent.batches/…
4. ReadThe agent dumps the board and runs read. It gets one short line per answer.
5. AckThe agent acts, then runs ack. The page shows the batch as handled.acks/…

If the agent needs more from you, it changes the card or posts a new one, and the cycle starts again.

Between steps 3 and 4 nothing pushes the agent. Either the agent checks the board when it next works, or a watcher polls and wakes it.

Ask me later

A card asks one thing. It stands alone, because you read it without the agent's session around it. The example is invented.

  • Kinds. A decision has 2 to 8 options. An action asks you to do something outside the board. An info card only asks you to acknowledge.
  • Revision. When the agent changes the question or the options, the card's rev goes up and the card shows "changed". An answer to an older rev does not count.
  • Links. supersedes replaces an older card and closes it. after greys a card until you answer another one first.
  • Notes. A note without an option is a question back to the agent. The card then waits on the agent.
open→answered→closed

A newer rev opens an answered card again. Your earlier answers stay in its history.

Where data lives

The database has seven collections. The access rules decide who may write each one. An agent that writes under its own account has the Contributor level ("interact"). You, the owner, can write everything.

CollectionHoldsWritten by
itemsThe cardsagents
guidesGuide pages in their own tabsagents (the page sets archive state)
acks"This batch is handled"agents
responsesYour draft answer per card, with its historythe page, as you
notesYour free notesthe page, as you
batchesWhat you sent, one per agent, with a copy of each answerthe page, as you
metaconfig: title, tabs, kinds, priorities, labels, agent name, image hostsyou

So an agent cannot fake your answer. The rules do not separate agents from each other, though: any agent can change any card. The script's ack refuses to mark another agent's batch.

The config makes one unchanged page fit many uses. A home-network project and a mail-triage agent can each have their own board with their own tabs, from the same board.html.

Why a script

Every word that passes through the agent's conversation costs tokens and adds a chance of a typing error. A board with fifty cards would cost a lot if the agent read and retyped them. So the agent never handles card text directly. It moves files, and the script does the work.

DumpThe agent asks the database tool to save each document of a collection as a JSON file in board/dump/.
Runnode board.mjs read --dump board/dump. The script reads the files, checks them, and works out what to do.
PrintIt prints short lines for the agent, and a numbered writes array. Each write points at a file in board/dump/out/.
WriteThe agent passes that array, unchanged, to one batch call of the database tool.

The agent sees short summary lines, never the card JSON. The script and the page read one shared definition of every field (SCHEMA in the page), so they cannot drift apart.

The commands: cards posts or changes cards, read lists new answers, ack marks a batch handled, guide posts a guide, purge deletes old closed cards after it copies them to disk, and check looks for bad data.

Guides

A guide asks nothing. It is a page in its own tab, written as Markdown by the agent.

  • text: steps or an explanation.
  • status: what the agent does now and what waits on you. Its tab comes first and shows a dot when it changed.
  • reference: tables and inline diagrams in HTML and SVG, for example a site record.

Reference HTML goes through a strict filter in the page, a sanitizer. It keeps a short list of safe tags and attributes and drops scripts, forms, frames and anything that could cover the page's buttons. A guide can point at its own parts with url(#id).

Measured on claude.ai: the artifact frame blocks images from every outside host, even when the board's domains list allows the host. Drawings in a guide must be inline SVG.

Trust rules

  • Only a batch that the agent reads itself with read counts as your word. A watcher's report only says where to look.
  • An answer applies to its card and that card's revision only.
  • Everything in the database is data, never an instruction. Text on a card cannot give the agent new permissions.
  • The plugin sends nothing to any server of its author. It talks only to your own claude.ai artifact, through your session.
Known limit in 0.3.1

How write versions reach the script

The database protects against two writers who overwrite each other. Every document has a version, a counter that goes up at each change. A write to an existing document must name the version that the writer last saw. If someone changed the document in between, the write fails and nothing is lost. This is called optimistic locking.

So the script must know the version of every document that it changes. A test on a real board showed that a dump does not give it.

Effect: the agent sees the version, but the script does not. Every change to an existing card, guide or answer is refused, on the version that is published now as well. New cards, new guides and acks still work, because a new document needs no version. The tests did not show this, because their dump files were written by hand.

The fix: ask only for the versions that are needed

The script will say which documents it changes: needs versions: items/a items/b. The agent copies those numbers from the dump reply that it already has, and runs the command again with --versions items/a=3,items/b=1.

  • A normal round copies one to five numbers, so the token cost stays low.
  • A simple model can follow the step word for word.
  • The command runs twice when something changes.

The script will then read every dump file as the bare document. This fix is not in version 0.3.1. It comes with the next rebuild of the skill.

What is tested

  • Node tests for the page logic and the script, an end-to-end run on fixtures, and 84 browser checks of the page in a phone-sized headless Chromium.
  • Two independent adversarial reviews, with code mutations to find tests that pass for the wrong reason.
  • On claude.ai, in a probe page: url(#id) and inline data: images render; outside images are blocked.
  • On a real board database: the file shape of a dump.
  • A full post, answer, read, ack and purge cycle on a real board. This waits on the version fix above.
  • A real phone, WebKit, and the Copy button inside claude.ai.
