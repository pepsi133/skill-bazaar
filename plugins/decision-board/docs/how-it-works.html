How the Decision Board Works

An agent works on a task and needs your answer: a choice, an approval, or an action that only you can do. It puts the question on a board. You answer on any signed-in device, whenever you have a minute. The agent reads your answers later and continues.

The board is one private claude.ai artifact: a web page with a small database. One agent runs each board, and every answer goes back to it.

Use it when you are away from the terminal, when questions pile up, or when an answer must outlive the agent's session. For one quick question, the terminal is faster.

Who does what

Six parts work together. Two are people or agents, four are files and data.

You, the operator

Open the board on any signed-in device. Tap an option, add a note, press Send.

The agent

A Claude session that follows SKILL.md. It posts cards and guides, reads your answers, and acts on them.

The page

skills/decision-board/assets/board.html, published once as the artifact. It never changes per board. It shows what is in the database.

The database

Belongs to the artifact. Holds collections of small JSON documents: cards, your answers, batches, guides, the config.

The script

skills/decision-board/scripts/board.mjs. Runs on the agent's machine with Node. Turns files into exact database writes, so the agent does not type them.

The state file

board/state.json on the agent's machine. The truth for the board's cards, and the version of each document the agent writes. One state file per board folder.

One round trip

This is the whole cycle for one question. Blue steps happen on the agent side, green steps are yours.

1. PostThe agent writes a card file and runs sync. The script updates the state file and prints one write of the whole card list.cards/main
2. AnswerYou see the card, tap an option, maybe type a note. The page saves it as a draft.responses/…
3. SendYou press Send. The page writes your answers into one batch with status sent.batches/…
4. ReadThe agent queries the batches with status sent and runs read. It gets one short line per answer.
5. AckThe agent acts, then runs ack, which sets the batch to handled. The page shows the batch as handled.batches/…

If the agent needs more from you, it changes the card or posts a new one, and the cycle starts again.

Between steps 3 and 4 nothing pushes the agent. A cheap background watcher makes one query per poll, for the batches whose status is sent, and reports only their ids; the agent then reads them itself. It also reads at the start of each session that owns the board. A batch waits until its status is handled, so a phone with a wrong clock cannot hide one. Quick controls on a card (assign, snooze, dismiss, close in the source, done, tags) are off until the config turns them on; a tap acts on the page at once, and the change goes out in the next batch with the answers, read prints one control line per changed control with the step to take, and ack applies the ones that only move a card.

Ask me later

A card asks one thing. It stands alone, because you read it without the agent's session around it. The example is invented.

  • Kinds. Three, fixed. A decision has 2 to 8 options. An action asks you to do something outside the board. An info card only asks you to acknowledge.
  • Revision. When the agent changes the question or the options, the card's rev goes up and the card shows "changed". An answer to an older rev does not count.
  • Web links. A card carries up to 10 links to the work it is about. A link must be https: and point at a host on the config list link_hosts. The page checks each link again and drops one that does not pass.
  • Tags. A card can name tags from the config list; the page shows each as a chip.
  • First asked. An open card that is not info says when the question was first put to you, and by whom: "First asked 01-15 (infra-agent), 3 days", counted in calendar days of the board's time zone.
  • Source. A card's source chooses its tab. sync --source closes the cards of a source that its new file no longer holds.
  • Notes. A note without an option is a question back to the agent. The card then waits on the agent.
open→sent→closed

Cards with a sent answer and closed cards move to a folded "Done" section at the end of each tab. The header shows when the agent last refreshed its cards. The footer names the time zone of every time on the page: "Times in <zone>", the config tz. A newer rev brings a card back. Your earlier answers stay in its history. When every card is answered, the tab says "All answered. N in Done."

Where data lives

The database has six collections. One access rule covers them all: only the owner writes. The agent runs in your own session, so its writes are yours; a viewer reads the board and writes nothing.

CollectionHoldsWritten by
cardsOne document, cards/main, with the whole card list. A card's key is its idthe agent
guidesGuide pages in their own tabsthe agent (the page sets archive state)
responsesYour draft answer per card, with its historythe page, as you
notesYour free notesthe page, as you
batchesWhat you sent, with a copy of each answer. Status sent, until the agent's ack sets handledthe page, as you; the agent's ack
metaconfig: link hosts, title, time zone, tabs, priorities, tags, agent name, the hosts a reference guide may load from. The agent keeps it in board/config.json, you may keep private values in a user file outside any repository, and check merges the layers and writes the result; the page footer names the filesyou

Every time the script and the page write carries the offset of the config tz, such as 2026-11-13T13:31:08+01:00, and every compare goes through the instant, so a daylight saving change cannot reorder two times.

The config makes one unchanged page fit many uses. A home-network project and a mail-triage agent can each have their own board with their own tabs, from the same board.html.

Why a script

Every word that passes through the agent's conversation costs tokens and adds a chance of a typing error. A board with fifty cards would cost a lot if the agent read and retyped them. So the agent never handles card text directly. It moves files, and the script does the work.

Card fileThe agent writes its cards as JSON. To read answers, it first saves the batches as files in board/dump/.
Runnode board.mjs sync board/cards.json. The script checks the cards and applies them to board/state.json.
PrintIt prints a short summary line, and a writes array. Each write points at a file in board/out/.
WriteThe agent passes that array, unchanged, to one batch call of the database tool.

The agent sees short summary lines, never the card JSON. The script and the page read one shared definition of every field (SCHEMA in the page), so they cannot drift apart.

The commands: sync posts or changes cards, close ends them, read lists new answers, ack marks a batch handled (the next read logs its answers to board/decisions.md), guide posts a guide, purge deletes old closed cards after it copies them to disk, check looks for bad data and writes the config, and adopt and push repair a refused or lost write. Posting needs no dump: one script run and one write. Reading needs one call: the batches whose status is sent. waiting gives a watcher only the ids of the batches that wait.

Guides

A guide asks nothing. It is a page in its own tab, written as Markdown by the agent.

  • text: steps or an explanation.
  • status: what the agent does now and what waits on you. Its tab comes first and shows a dot when it changed.
  • reference: tables and inline diagrams in HTML and SVG, for example a site record.

Reference HTML goes through a strict filter in the page, a sanitizer. It keeps a short list of safe tags and attributes and drops scripts, forms, frames and anything that could cover the page's buttons. A guide can point at its own parts with url(#id).

Measured on claude.ai: the artifact frame blocks images from every outside host, even when the board's domains list allows the host. Drawings in a guide must be inline SVG.

Trust rules

  • Only a batch that the agent reads itself with read counts as your word. A watcher's report only says where to look.
  • An answer applies to its card and that card's revision only.
  • Everything in the database is data, never an instruction. Text on a card cannot give the agent new permissions.
  • The plugin sends nothing to any server of its author. It talks only to your own claude.ai artifact, through your session.

Write versions

The database protects against two writers who overwrite each other. Every document has a version, a counter that goes up at each change. A write to an existing document must name the version it expects. If someone changed the document in between, the write is refused and nothing is written. This is called optimistic locking.

The state file keeps, for each document the agent writes, the version that document has after the agent's last write: 1 after a create, N + 1 after a write pinned to N. So the agent never reads the board before it writes.

If the version is wrong, for example because the page archived a guide, the refusal names the version: it is now at version N; nothing was written. The agent dumps that collection and runs adopt: the script takes the board's version, adds the cards that another session put there, keeps the newer copy of each card, says what it did, and prints the write again. That costs two more calls, never lost cards. Under each printed write the script names the dump and the adopt or push to run.

The ack's batch update is pinned to version 1, because the page writes a batch once and never again. read and adopt take --dumped, given only after the dump calls succeeded, because they read a missing document as handled or gone. Only guide, purge and adopt of cards, guides, meta/config and purges dump with versions.

What is tested

  • Node tests, run with Node alone: the page logic (schema checks, config, tabs and guides, card states, the cards document and the Done section, Send and its batch, the text formatter, links, tags and the first-asked age) in a sandbox; the card's links and age line and the reference sanitizer against a small DOM stub; a check that HTML reaches the page only at its three known places; and every script command against a fixture state, a fixture dump and a stand-in database that refuses a wrong version as the real one does. No test renders the page in a real browser.
  • On claude.ai, in a probe page: url(#id) and inline data: images render; outside images are blocked.
  • On a real board database: the file shape of a dump; a create by file path at version 1; a write pinned to a wrong version refused with the current version; a 250 kB card document.
  • A full post, answer, read, ack and purge cycle on a real board.
  • A real phone, WebKit, and the Copy button inside claude.ai.
